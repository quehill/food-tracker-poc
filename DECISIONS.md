# Decisions

Running log of choices made while building the POC. Format: decision, reason, alternatives considered.

## Phase 0

### Stack versions: Vite 6, React 19, React Router 7, Dexie 4, Vitest 3, ESLint 9

- **Reason:** current stable majors with well-known APIs; boring choices.
- **Alternatives:** newer majors where available; deferred until there's a reason.

### No state library (no Zustand)

- **Reason:** state is either persisted (IndexedDB via repositories) or local to a screen. A tiny change-notification hook (`useRepoQuery`) re-reads repositories after writes. Nothing global left for Zustand to hold.
- **Alternatives:** Zustand; `dexie-react-hooks` `useLiveQuery` (rejected because it would couple the UI to Dexie).

### Hash routing via `createHashRouter`

- **Reason:** GitHub Pages has no SPA rewrites; hash routes never 404 on refresh or deep link.
- **Alternatives:** 404.html redirect hack (fragile).

### Base path from `VITE_BASE_PATH`

- **Reason:** project Pages sites live under `/<repo>/`. CI sets it from the repository name; locally it defaults to `/`. Manifest `start_url`/`scope` and the service worker scope use the same value. `index.html` uses `%BASE_URL%` for icon links.

### PWA: `vite-plugin-pwa`, `registerType: 'prompt'`

- **Reason:** avoids pinning users to stale builds while never reloading under them mid-entry. Update checks on resume (`visibilitychange`) and hourly because installed iOS PWAs are rarely cold-started.
- **Added dependency:** `workbox-window` (required peer for the plugin's register module).

### Placeholder icons generated by a script

- **Reason:** no binary tooling dependency. `scripts/generate-icons.mjs` writes simple PNGs with Node's zlib. Maskable icon keeps the mark inside the 40% safe-zone radius.

### `domain/` purity enforced by ESLint

- **Reason:** `no-restricted-imports` / `no-restricted-globals` on `src/domain/**` keeps it portable to iOS.

### `fake-indexeddb` (dev dependency)

- **Reason:** run repository/Dexie tests in Node without a browser.

### `.nvmrc` = 22

- **Reason:** LTS line for CI; the code has no Node-version-specific features.

### CI: single build job, deploy job only on `main` pushes

- **Reason:** PRs run the same check + build (catches base-path build breaks) but never deploy. `concurrency: pages` on the deploy job prevents overlapping deploys without cancelling an in-progress one.

## Phase 1

### Selected day lives in the URL (`#/?date=YYYY-MM-DD`, `#/add?date=...`)

- **Reason:** survives reload, needs no global state, and the Add screen knows which day to log to. Omitted when the day is today.

### Entries snapshot `servingLabel` as well as name and macros

- **Reason:** the Today list shows "1.5 × 3 oz" correctly even after the food is edited or deleted. Additive optional field on `LogEntry`.

### Editing an entry's servings rescales its own snapshot

- **Reason:** `newMacros = snapshot × newServings / oldServings`. Never re-reads the current food, so history is never rewritten.

### Logging to a past/future day uses the current wall-clock time on that date

- **Reason:** keeps chronological ordering sensible without asking for a time.

### Delete entry/food via `window.confirm`

- **Reason:** simplest accessible confirmation; works on iOS. Swipe-to-delete skipped to avoid a gesture dependency.
- **Alternatives:** undo toast (nicer; revisit in Phase 5 polish).

### Calorie mismatch warning offers "Use N kcal"

- **Reason:** soft warning per spec (never blocks save), with a one-tap fix using 4P + 4C + 9F.

### Default targets: 2000 kcal, 150 g protein; carbs/fat unset

- **Reason:** placeholders the owner edits in Settings. Carbs/fat targets are optional; without one, only the consumed amount is shown.

### Sample data loader is in a collapsed "Developer" section in Settings (always available)

- **Reason:** the owner tests on the deployed site on an iPhone, so a dev-build-only button wouldn't be reachable. Uses fixed ids, so loading twice is a no-op. Sample meal ("Turkey sandwich") arrives with Phase 2. Gram weights for egg/banana/bread/cheese are approximate.

### IDs: `crypto.randomUUID()` with a `getRandomValues` fallback

- **Reason:** `randomUUID` requires a secure context; the fallback lets the app work over plain-HTTP LAN during development.

### Add screen (Phase 1 version) lists all foods by recency with a "+1" one-tap log

- **Reason:** satisfies quick-add now; Favorites/Recents sections and meal search come in Phase 3.

## Phase 2

### Meal ingredient quantity stored as servings; grams input synced when the food has serving grams

- **Reason:** matches `MealItem { foodId, servings }`. "85 g turkey" is entered as grams and converted (servings = grams / serving grams).

### Deleting a food used in meals is allowed, with a warning naming the meals

- **Reason:** blocking would force the user to edit meals first. Meals keep the dangling reference, show "Deleted food", and can't be logged or saved until it's removed, so a meal is never logged with silently missing calories.
- **Alternatives:** cascade-remove the ingredient from meals (silently changes meals); block deletion.

### A logged meal is one entry (`kind: 'meal'`) with summed macros, serving label "meal"

- **Reason:** keeps Today's list short; servings multiplier rescales the snapshot like food entries. Per-ingredient breakdown isn't stored in the entry.

### "Save & log" on the meal builder logs to today

- **Reason:** the builder has no date context. Logging from the Meals list respects `?date=` like the Add screen.

### Meals list sorted alphabetically; meal search and favorites/recents on the Add screen come in Phase 3

### USDA search inside the meal builder deferred to Phase 4 (with the provider)

## Phase 3

### Add screen sections: Favorites, Recent, then everything else alphabetically

- **Reason:** favorites are one tap ("+1") from the Add screen, so a favorite is two taps from Today (Add, +1). An "All" section keeps everything reachable before there's any history.
- Favorites sort by use count; Recent = used non-favorites sorted by last used, use count breaks ties, max 10. Favorites are not repeated in Recent.

### Search covers foods and meals together; all query words must match

- **Reason:** "turkey sand" should find the meal. Ranking: name starts with query, then a word starts with it, then other matches (including brand); favorites and recent use break ties. Ranking logic lives in `domain/quickAdd.ts` and is unit tested.

### "+1" shows an Undo, which also restores the item's usage stats

- **Reason:** one-tap logging makes accidental taps likely; undo removes the entry and keeps Recents accurate. Only the last quick log can be undone.

### Meals with deleted ingredients appear but can't be logged

- **Reason:** consistent with Phase 2; the row explains why and the sheet links to the meal editor.
