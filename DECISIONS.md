# Decisions

Running log of choices made while building the POC. Format: decision, reason, alternatives considered.

## Phase 0

### Stack versions: Vite 6, React 19, React Router 7, Dexie 4, Vitest 3, ESLint 9

- **Reason:** current stable majors with well-known APIs; boring choices.
- **Alternatives:** newer majors where available; deferred until there's a reason.

### No state library (no Zustand)

- **Reason:** state is either persisted (IndexedDB via repositories) or local to a screen. A tiny change-notification hook (`useRepoQuery`) re-reads repositories after writes. Nothing global left for Zustand to hold.
- **Alternatives:** Zustand; `dexie-react-hooks` `useLiveQuery` (rejected because it would couple the UI to Dexie).

### Hash routing via `createHashRouter`

- **Reason:** GitHub Pages has no SPA rewrites; hash routes never 404 on refresh or deep link.
- **Alternatives:** 404.html redirect hack (fragile).

### Base path from `VITE_BASE_PATH`

- **Reason:** project Pages sites live under `/<repo>/`. CI sets it from the repository name; locally it defaults to `/`. Manifest `start_url`/`scope` and the service worker scope use the same value. `index.html` uses `%BASE_URL%` for icon links.

### PWA: `vite-plugin-pwa`, `registerType: 'prompt'`

- **Reason:** avoids pinning users to stale builds while never reloading under them mid-entry. Update checks on resume (`visibilitychange`) and hourly because installed iOS PWAs are rarely cold-started.
- **Added dependency:** `workbox-window` (required peer for the plugin's register module).

### Placeholder icons generated by a script

- **Reason:** no binary tooling dependency. `scripts/generate-icons.mjs` writes simple PNGs with Node's zlib. Maskable icon keeps the mark inside the 40% safe-zone radius.

### `domain/` purity enforced by ESLint

- **Reason:** `no-restricted-imports` / `no-restricted-globals` on `src/domain/**` keeps it portable to iOS.

### `fake-indexeddb` (dev dependency)

- **Reason:** run repository/Dexie tests in Node without a browser.

### `.nvmrc` = 22

- **Reason:** LTS line for CI; the code has no Node-version-specific features.

### CI: single build job, deploy job only on `main` pushes

- **Reason:** PRs run the same check + build (catches base-path build breaks) but never deploy. `concurrency: pages` on the deploy job prevents overlapping deploys without cancelling an in-progress one.

## Phase 1

### Selected day lives in the URL (`#/?date=YYYY-MM-DD`, `#/add?date=...`)

- **Reason:** survives reload, needs no global state, and the Add screen knows which day to log to. Omitted when the day is today.

### Entries snapshot `servingLabel` as well as name and macros

- **Reason:** the Today list shows "1.5 × 3 oz" correctly even after the food is edited or deleted. Additive optional field on `LogEntry`.

### Editing an entry's servings rescales its own snapshot

- **Reason:** `newMacros = snapshot × newServings / oldServings`. Never re-reads the current food, so history is never rewritten.

### Logging to a past/future day uses the current wall-clock time on that date

- **Reason:** keeps chronological ordering sensible without asking for a time.

### Delete entry/food via `window.confirm`

- **Reason:** simplest accessible confirmation; works on iOS. Swipe-to-delete skipped to avoid a gesture dependency.
- **Alternatives:** undo toast (nicer; revisit in Phase 5 polish).

### Calorie mismatch warning offers "Use N kcal"

- **Reason:** soft warning per spec (never blocks save), with a one-tap fix using 4P + 4C + 9F.

### Default targets: 2000 kcal, 150 g protein; carbs/fat unset

- **Reason:** placeholders the owner edits in Settings. Carbs/fat targets are optional; without one, only the consumed amount is shown.

### Sample data loader is in a collapsed "Developer" section in Settings (always available)

- **Reason:** the owner tests on the deployed site on an iPhone, so a dev-build-only button wouldn't be reachable. Uses fixed ids, so loading twice is a no-op. Sample meal ("Turkey sandwich") arrives with Phase 2. Gram weights for egg/banana/bread/cheese are approximate.

### IDs: `crypto.randomUUID()` with a `getRandomValues` fallback

- **Reason:** `randomUUID` requires a secure context; the fallback lets the app work over plain-HTTP LAN during development.

### Add screen (Phase 1 version) lists all foods by recency with a "+1" one-tap log

- **Reason:** satisfies quick-add now; Favorites/Recents sections and meal search come in Phase 3.

## Phase 2

### Meal ingredient quantity stored as servings; grams input synced when the food has serving grams

- **Reason:** matches `MealItem { foodId, servings }`. "85 g turkey" is entered as grams and converted (servings = grams / serving grams).

### Deleting a food used in meals is allowed, with a warning naming the meals

- **Reason:** blocking would force the user to edit meals first. Meals keep the dangling reference, show "Deleted food", and can't be logged or saved until it's removed, so a meal is never logged with silently missing calories.
- **Alternatives:** cascade-remove the ingredient from meals (silently changes meals); block deletion.

### A logged meal is one entry (`kind: 'meal'`) with summed macros, serving label "meal"

- **Reason:** keeps Today's list short; servings multiplier rescales the snapshot like food entries. Per-ingredient breakdown isn't stored in the entry.

### "Save & log" on the meal builder logs to today

- **Reason:** the builder has no date context. Logging from the Meals list respects `?date=` like the Add screen.

### Meals list sorted alphabetically; meal search and favorites/recents on the Add screen come in Phase 3

### USDA search inside the meal builder deferred to Phase 4 (with the provider)

## Phase 3

### Add screen sections: Favorites, Recent, then everything else alphabetically

- **Reason:** favorites are one tap ("+1") from the Add screen, so a favorite is two taps from Today (Add, +1). An "All" section keeps everything reachable before there's any history.
- Favorites sort by use count; Recent = used non-favorites sorted by last used, use count breaks ties, max 10. Favorites are not repeated in Recent.

### Search covers foods and meals together; all query words must match

- **Reason:** "turkey sand" should find the meal. Ranking: name starts with query, then a word starts with it, then other matches (including brand); favorites and recent use break ties. Ranking logic lives in `domain/quickAdd.ts` and is unit tested.

### "+1" shows an Undo, which also restores the item's usage stats

- **Reason:** one-tap logging makes accidental taps likely; undo removes the entry and keeps Recents accurate. Only the last quick log can be undone.

### Meals with deleted ingredients appear but can't be logged

- **Reason:** consistent with Phase 2; the row explains why and the sheet links to the meal editor.

## Phase 4

### Two USDA requests per search: generic (Foundation, SR Legacy) and Branded, in parallel

- **Reason:** in one combined request, branded items fill the first page (a "turkey breast" search returned only branded hits), so generic results couldn't be ranked first. Cost is 2 requests per (debounced, cached) search, well within 1,000/hour.
- **Alternatives:** one request sorted by `dataType` (loses relevance order).

### Light re-rank within each group by query-word matches in the name

- **Reason:** USDA relevance alone put "Rolls, dinner, oat bran" first for "rolled oats". Stable sort, so USDA order is kept among equal matches.
- **Superseded (post-Phase 5), see below.**

### Search relevance v2: all-words first, brand-aware ranking across groups

- **Problem:** "premier protein shake" returned Toll House "Premier White" morsels and generic shake mixes; the actual Premier Protein shake was 6th in branded and always behind every generic result.
- **Change:** each group (generic, branded) first requests `requireAllWords=true` (USDA matches words across description and brand). If that yields fewer than 5 items, an any-word request tops it up (skipped for one-word queries). Results are then ranked together by query words matched in name + brand, then words matched in the name; ties keep generic before branded and USDA order. Duplicates are removed.
- **Cost:** 2 requests for most searches, up to 4 for sparse multi-word queries; debounced and cached, well within 1,000/hour.
- **Effect (live):** Premier Protein shakes fill the top 5; "turkey breast", "greek yogurt plain" still lead with generic items; "rolled oats" leads with generic rolled oats followed by branded rolled oats.

### Include Survey (FNDDS) in the generic group; search via POST

- **Reason:** FNDDS covers mixed dishes and restaurant items (e.g. "McDouble (McDonalds)") that aren't in Foundation/SR Legacy or Branded.
- **Serving:** FNDDS items use a real portion instead of 100 g, e.g. "1 double cheeseburger (140 g)". USDA's rank-1 portion isn't always the item (Big Mac's is "1 McDonald's Mac Jr"), so the portion sharing the most words with the description wins, then rank; "Quantity not specified" is skipped.
- **POST instead of GET:** GET requests with `dataType=Survey (FNDDS)` in the query string intermittently returned nginx 400s (about half the time in testing); POST with a JSON body was reliable. Only the API key stays in the URL.

### Energy: 1008 (kcal), then 2048/2047 (USDA Atwater energy), then our own Atwater estimate

- **Reason:** many Foundation foods have no 1008 but do have USDA-computed Atwater energy (2047/2048); those are USDA values, so not marked estimated. Only our own 4/4/9 fallback sets `caloriesEstimated`. kJ values are ignored. Negative nutrient values (USDA "by difference" quirk) are clamped to 0.

### Serving conversion

- Search-result nutrients are per 100 g (100 ml for liquids). If the item has `servingSize` in g/ml, macros are scaled to it and the label uses the household text (e.g. "2 oz (57 g)"; USDA's "ONZ" shown as "oz"). Otherwise the serving is 100 g. ml servings don't get a grams value. ALL-CAPS branded names are title-cased.

### Import flow: preview sheet with "Save & edit" or "Save & log"; re-importing the same fdcId reuses the existing food

- **Reason:** explicit save (no accidental imports), explains the per-100 g scaling, and avoids duplicate foods. In the meal builder, tapping a USDA result imports it and adds it as an ingredient.

### Missing key -> provider is `null`, lookup UI explains and links to manual entry; build still succeeds

### Fixtures are trimmed real responses recorded with `DEMO_KEY` (only the fields the mapper reads)

### Provider code (`src/providers/`) may import `domain/` (pure), never the reverse

## Phase 5

### Serving grams changes rescale macros automatically (owner request)

- **How:** the food form keeps a base (macros at a known serving weight, taken from the saved food or the last manual macro edit). Changing serving grams sets macros = base × newGrams / baseGrams, so typing "8" then "85" never drifts. A label like "100 g" is updated to match. A checkbox turns it off (e.g. to correct a mistyped weight without touching macros).
- Exact (unrounded) values are saved when the field still shows them; the "calories estimated" flag survives a pure rescale.
- No scaling when the food had no serving grams before (adding a weight just describes the serving).

### Backup format: `{ app, schemaVersion, exportedAt, foods, meals, logEntries, settings }`

- **Reason:** mirrors the stores, simple to diff and restore. Every record is shape-checked on import; errors name the bad record. Newer `schemaVersion` is rejected; older versions go through a migration table (empty at v1).
- Import **replaces** everything in one IndexedDB transaction (no partial restores). Merge was rejected: ambiguous on id conflicts and rarely what you want when restoring.
- `lastBackupAt` is device-local: excluded from backups and kept on restore.

### Saving files: share sheet on touch devices, download link elsewhere

- **Reason:** in installed iOS PWAs, blob downloads open a preview that's hard to leave; the share sheet's "Save to Files" is reliable. Desktop uses a normal download.

### CSV: RFC 4180 quoting, UTF-8 BOM, values rounded to 2 decimals, formula-like text prefixed with `'`

- **Reason:** opens cleanly in Excel; prevents spreadsheet formula injection from food names.

### `navigator.storage.persist()` on every launch; status and manual request in Settings

- **Reason:** browsers decide silently (Chrome/Safari) so there's no prompt cost. Backup reminder after 7 days or when data exists but was never backed up.

### "Clear all data" in Settings

- **Reason:** needed for the export, clear, import acceptance check and for moving between the Safari tab and installed app.

### "Units display" setting not added

- **Reason:** the app only tracks kcal and grams (spec), so there's nothing to switch. Revisit if kJ or ounces are wanted.

### Accessibility pass

- Labeled inputs everywhere; field errors linked with `aria-describedby`; required fields marked; status regions use `aria-live`; icon buttons have labels; tab bar uses `aria-current`; sheets are native `<dialog>` (focus trap, Escape); visible focus ring; light/dark via `prefers-color-scheme` with AA contrast.

## Post-POC: target calculator, Today redesign, Trends

### Charts added, though the original spec listed them as out of scope (owner request)

- **How:** hand-drawn SVG rings (`Ring.tsx`) and CSS stacked bars (`TrendChart.tsx`); no chart library.
- **Reason:** the spec asks for minimal dependencies, and two chart types don't justify one (Recharts/Chart.js add 50–150 KB gzipped). Plain SVG/CSS also maps directly to SwiftUI shapes for the iOS port.

### Target estimate: Mifflin-St Jeor × activity factor, goal offset, protein/fat by body weight, carbs as the remainder

- **BMR:** Mifflin-St Jeor (Mifflin et al., Am J Clin Nutr 1990;51:241). The ADA systematic review (Frankenfield et al., J Am Diet Assoc 2005;105:775) found it the most reliable common equation, usually within 10% of measured RMR. Harris-Benedict overestimates by about 5%; Katch-McArdle needs body-fat %, which most users don't know.
- **Activity factors:** 1.2 / 1.375 / 1.55 / 1.725 / 1.9 (the standard sedentary to extremely active multipliers).
- **Goal:** −500 / −250 / 0 / +250 kcal per day (lose 1 lb, lose ½ lb, maintain, gain ½ lb per week, using about 3,500 kcal per lb). Floor of 1,500 kcal (men) / 1,200 kcal (women), with a notice when it applies.
- **Protein:** 1.6 g/kg; Morton et al. (Br J Sports Med 2018) found no further fat-free-mass gain above ~1.62 g/kg/day. 2.0 g/kg in a deficit to help preserve lean mass. At BMI ≥ 30, the weight at BMI 25 is used, because per-kg rules on total weight overshoot.
- **Fat:** 30% of calories (IOM acceptable range 20–35%), at least 0.6 g/kg. **Carbs:** remaining calories ÷ 4, using the app's existing 4/4/9 factors.
- **Rounding:** kcal to the nearest 10, grams to the nearest 5 (the macros' energy stays within about 25 kcal of the target).
- **Inputs:** sex (male/female; the equation only has those two constants), age (18–100), height in ft/in, weight in lb. Stored in metric in a `profile` setting so the formulas stay unit-free.
- **Prefill, not auto:** "Use these targets" fills the target fields; the user reviews and saves. Targets stay fully editable, and changing weight later doesn't move them silently.

### Target history: `targetHistory` setting of `{ effectiveFrom, targets }[]`

- **Reason:** Trends compares each day to the target in effect that day, so changing targets doesn't rewrite the past (the same idea as entry snapshots). Saving targets replaces any period starting today or later and keeps earlier ones.
- **Compatibility:** the `targets` key still holds the latest targets. Without a history (older data or backups), the current targets cover all dates. No Dexie schema bump was needed: settings is key/value, and backups already include every non-local setting.
- Today also uses the targets for the selected day.

### Trends: last 7 days, ‹ › by week (`#/trends?end=YYYY-MM-DD`)

- Bar height = logged calories. Segments split it by each macro's share of 4/4/9 energy, so label calories (which don't always match 4/4/9) still set the height. A day with calories but no macros shows a neutral bar.
- The dashed per-day target line steps when the target changed. Today's bar is faded (in progress).
- Averages leave out today and days with nothing logged, so an unlogged day doesn't count as 0 kcal. A macro's average target is shown only when every counted day had that target; otherwise only the average intake is shown.
- "On target" = calories within ±10% of that day's target.
- Each bar is a link to that day with a full text label (date, kcal vs target, P/C/F grams), so screen readers get the data without a separate table.
- Range query `listByDateRange` uses the existing `date` index.

### Navigation: Today | Add | Foods | Trends | Settings; Meals moved under Foods

- **Reason:** six tabs are cramped at 390 px. Foods and Meals are both library management, so they share a tab with a Foods | Meals switch. `/meals` routes are unchanged and keep the Foods tab highlighted.

### Macro colors

- Protein blue, carbs amber, fat pink, the same on Today and Trends; calories use the accent green and overflow uses the danger red. Light-mode shades are dark enough for ≥3:1 non-text contrast on the card background; dark mode uses lighter tints.

### Today summary compacted to about the top third of the screen (owner request)

- **Replaces** the large calorie ring + separate split donut. Now one 124 px double ring sits beside the macro bars: the outer track is calories vs target (center: kcal left/over), and the inner track is the P/C/F calorie split. Each macro row shows "g left · % of kcal", so the split has a text form too.
- At 390×844 the card ends about 257 px down (under a third of the screen), leaving the rest for entries.

### iOS status bar: keep `status-bar-style="default"`; add a fixed opaque backdrop at the top

- iOS 27 betas draw a progressive blur over the top edge of installed PWAs that use `black-translucent`, with no CSS or meta opt-out. Reported fix: use `default`, which this app has used since Phase 0. The meta is frozen at install, so changing it needs a re-add to the Home Screen.
- A real fixed element (`.status-bar-backdrop`, height `max(1px, safe-area-inset-top)`, `background: var(--bg)`) gives iOS a solid color to sample for the status bar, and nothing scrolls under it. Pseudo-elements reportedly aren't sampled.
- **Known limitation:** in standalone mode `prefers-color-scheme` is reportedly frozen per process, so after switching iOS light/dark the status bar color can be wrong until the app is relaunched.
